- (decision) Invariant 1, UI THREAD IS SACRED: TRestServer.Uri() never runs inside the webview_bind callback. The callback is treated as UI-affine by internal convention (upstream does not document the callback thread) and does only validate size, copy id/request, capture InvocationContext, enqueue, return. No SQLite, disk, SOA or heavy crypto in it. Rationale: upstream states the webview_run thread is the GUI thread and its functions carry no general thread-safety guarantee.
- (decision) Results return by calling webview_return() directly from the worker: upstream documents it as thread-safe and already performing the dispatch it needs, so wrapping it in webview_dispatch() is redundant and forbidden.
- (decision) GUI-affine commands (window.setTitle, window.minimize, window.close) run the opposite way: RPC worker calls webview_dispatch() to schedule the operation on the GUI loop thread, which is what upstream defines webview_dispatch for.
- (constraint) Per-WebView backpressure from Phase 0: a maximum number of simultaneous invocations and a maximum queue size, because an enthusiastic React UI can trivially emit hundreds of requests. Limits are configurable; the mechanism is fixed, the numbers are not.
- (constraint) No ordering guarantee between concurrent invocations: two native.invoke() calls may complete in either order. Ordering is obtained by awaiting sequentially or by transactional semantics inside the service — never assumed by the bridge.
- (decision) Invariant 2, EVERGREEN FIRST: WebView2 Evergreen is the Windows default (shared runtime, self-updating, smaller footprint, bundled in Windows 11 and present on most eligible Windows 10 machines per Microsoft). pweb build gains three profiles: normal (installer checks presence, ~2MB bootstrapper if absent), offline (Evergreen Standalone Installer embedded), fixed-runtime (opt-in only). The runtime check happens at setup time, not at first launch failure.
- (constraint) Fixed Runtime WebView2 is opt-in only, reserved for frozen industrial, certified, kiosk or regulated environments: Microsoft puts it at 250MB+ added to distributed binaries and it makes us responsible for its updates, which would turn a no-250MB-Electron project into a 250MB project of our own.
- (decision) Invariant 3, JSON IS NOT BINARY: native.invoke() is the control plane, pweb://blob is the data plane. Upstream webview_bind receives a JSON argument array and webview_return requires valid JSON, which is right for a method+id envelope and wrong for an 80MB PDF; base64 only adds size, allocations and copies.
- (decision) A service returning bulk data answers with a BlobHandle envelope (kind, id, size, mime, url=pweb://blob/{token}); the frontend then does fetch(url) and reads it as a blob or stream. Reuses the existing pweb:// resource-handler infrastructure instead of inventing a second transport.
- (decision) IBlobStore backs pweb://blob with memory, file, archive and generated-stream sources. Range, Content-Length, Content-Type, ETag and Cache-Control are supported early so a <video> seeking to the last three seconds does not force 2GB into memory. Platform basis: WebView2 WebResourceRequested can supply a response body as a stream, WebKitGTK can finish a scheme request with a GInputStream including asynchronously, and WKURLSchemeHandler/WKURLSchemeTask expose the same model on Apple.
- (decision) JS to native blob transport: the SDK surface is frozen now (native.blobs.create(file), backed by IBlobStore/IBlobReader/IBlobWriter) but the transport is deliberately NOT frozen. WebView2 accepts a request body as a stream and WebKitGTK exposes webkit_uri_scheme_request_get_http_body() since 2.40, but a fetch(PUT pweb://...) universal protocol is only declared after real macOS integration tests against WKURLSchemeTask URLRequest. JSON chunking exists as a fallback only, never as the nominal path.
- (constraint) WebView2 SharedBuffer (surfacing in JS as an ArrayBuffer) is a Windows fast path behind IWebBlobTransport, never part of the public PWeb contract, otherwise the cross-platform abstraction disintegrates.
- (decision) Invariant 4, CAPABILITY IS CONTEXTUAL: neither pure static manifest nor pure runtime scoping. The app manifest is an absolute ceiling and effective rights are EffectiveCapabilities = AppMaximum AND PrincipalCapabilities AND WindowCapabilities AND RuntimeGrants. Example: a MainWindow gets most of the app ceiling, a LoginWindow only settings.read plus window.control, a ReportingPlugin only parking.read.
- (constraint) Authorization never trusts a JS-supplied field. Upstream webview_bind delivers only request id, JSON request and user argument, with no origin in its C contract, so an origin sent inside the JSON payload is worthless. TInvocationContext (WindowId, PrincipalId, PrincipalKind, Capabilities, PluginId, TrustedContent) is constructed natively and attached to the bridge instance; JS sends method and arguments only.
- (constraint) A privileged WebView may navigate only within pweb://app/...; https: and mailto: links open in the system browser. External content is never executed in a WebView holding the privileged bridge. If embedded external content is ever needed it runs in a separate WebView with empty or microscopically scoped capabilities.
- (decision) Plugins are first-class principals: pkWindow, pkPlugin, pkSystem, pkQuickJS. QuickJS therefore reuses the identical permission system rather than growing a second, incompatible one later.
- (capability) CAP-12 large binary payloads over the data plane: the frontend reads and writes bulk binary data without base64 on the JSON bridge. Success: a service returning a >40MB PDF answers with a BlobHandle, the frontend fetches pweb://blob/{token}, and the response honours Range, Content-Length and Content-Type without buffering the whole payload in memory.
