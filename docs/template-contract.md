# The PWeb template contract (CAP-10B0)

The private scaffolding engine frozen by CAP-10B0: where templates come
from, what is allowed to be trusted about them, how a project's identity is
decided, and what `pweb create` will do when CAP-10B1 exposes it.

Everything here is a **contract**. The wording may be improved freely; the
carrier, the trust anchor, the identity mapping, the placeholder set, the
line-ending rule, the bounds and the transaction may not, except by a
version bump.

**`pweb create` does not exist in this build.** It is not a stub, it is not
listed in `--help`, and it is not merely undispatched: the scaffold engine
is **not linked into the `pweb` executable at all**, and
`test/cap10b0/check_cap10b0_contracts.ps1` measures that against the CLI's
compiled unit set on every CI leg. CAP-10B0 freezes an engine; CAP-10B1 and
CAP-10B2 give it a template worth shipping and a command to reach it.

---

## 1. The carrier

```
  <sdk-root>/
    bin/
      pweb[.exe]                        the executable
    share/
      pweb/
        pweb-templates.zip              the trusted template pack
```

One rule resolves it, and it starts from the running image:

> **sdk-root = parent(canonical directory of the running executable)**

Never the working directory. Never a value from `pweb.json`, from `app.pwb`,
from a frontend or from a build output. **Never an environment variable** —
there is no `PWEB_HOME`, no `PWEB_SDK` and no `PWEB_TEMPLATES`, and the
contract check sweeps the engine for every spelling of one, including a bare
`getenv`. A developer tool that can be pointed at a different SDK by
exporting a variable is a tool whose trusted input is whatever the last
shell profile said it was.

There is exactly **one shape**, not a search. A basename test ("am I in a
directory called `bin`?") would be two shapes and a guess about which
applies; walking up the tree would make the answer depend on what happens to
exist above the executable. `share`, `pweb` and the pack name are then
resolved **one component at a time**, each matched against its exact on-disk
spelling read from the directory itself, with a reparse point at any
position refusing the whole path — the same discipline `pweb.cli.paths`
applies to project paths.

Callers that need a different root — a test staging a fixture SDK, a
developer build — pass it as a **parameter**. That is the whole of the seam:
an argument at a call site, visible in the source, never an ambient input
the process reads behind its own back.

### Why an adjacent archive

| model | why not |
|---|---|
| archive embedded in the executable | inflates the binary with a generated byte array, makes every template edit a recompile of the public CLI, and destroys the CAP-10A `cli-units` evidence that makes "no network" mechanical |
| an installed loose directory | the trusted input becomes N filesystem objects with N reparse, case and permission questions instead of one hashed blob, and there is no read-once-and-hash point, so a window opens between verifying the tree and reading the files |

The adjacent archive reuses the ratified CAP-9C1 shape: **one** handle,
reparse refused, size bounded *before* reading, hashed while read, and the
bytes that were hashed are the bytes that are parsed. There is no second
read, so there is no check-then-open race to lose.

`pweb-templates.zip` is deliberately neither `app.pwb` nor `plugins.zip`.
Both of those carry frozen, structurally different contracts, and a third
archive must not be mistakable for either.

## 2. The trust anchor

**The archive carries bytes. It carries nothing else, and it is believed
about nothing else.**

Every name, every output path, every content kind, every file mode, every
byte length, every digest and the set of template ids themselves are
**compiled constants**, generated by the trusted build into
`pweb.templates.registry.inc` and compiled in with `-Fi` under
`{$WRITEABLECONST OFF}`.

So a substituted or tampered pack cannot:

- redirect an output path — the mapping is not in the archive;
- mark a generated file executable — the mode is not in the archive, and
  *could not be*: the deterministic writer zeroes the ZIP external
  attributes, so the format is structurally incapable of carrying one;
- reclassify a binary as text and so become subject to substitution;
- add, remove or rename a file — the inventory is compared entry by entry
  **and the entry count is compared too**, so an archive holding the right
  number of the wrong things fails, and so does one holding an extra file;
- redefine its own expected hash;
- offer a template id the CLI does not already know;
- make a **private** template reachable from a public command.

### Verification order, and why it is that order

```
registry self-consistency          (before ANY byte is believed)
    -> the pack bytes, read ONCE while hashing
    -> exact byte length, then exact SHA-256
    -> TZipAssetStore over THOSE SAME BYTES
    -> the entry count, then the semantic inventory entry by entry
    -> only then does a store escape
```

On any failure no store is produced at all, so there is no half-verified
archive for a caller to be tempted by.

## 3. The trusted source, and the deterministic pack

```
tools/templates/
  templates.list          the build-time declaration
  <template-id>/          the template's own files, LITERAL names
```

`tools/templates/` is deliberately not under `tools/pweb/`: that directory
is inside the CAP-7F divergence sweep, and a Pas2JS template will ship
`.pas` files that have no business being judged for platform conditionals.

**Every file is declared explicitly** — its output path, its content kind
and its file mode — and the builder cross-checks the declaration against the
directory **in both directions**. A file on disk that nobody declared is an
error; a declared file that is not on disk is an error. Nothing is inferred
from an extension, because the two mistakes that matter in this class —
substituting inside a binary, and shipping a credential — are exactly the
ones an extension rule gets wrong.

The **source path is literal; the `out` path may carry placeholders.**
Keeping the two apart is what lets a template ship a file called
`gitignore` and generate `.gitignore`, without a dot-file inside this
repository quietly changing what git tracks here.

### The list grammar

The repository's existing `key = value` lock-file grammar: `#` comments,
blank lines ignored, ASCII only, no escape sequence anywhere, bounded at
64 KiB. `schema` first and exactly once, `template` opens a block, `file`
opens a file block inside it, every key at most once per block. **An
unknown key is a hard error, and so is an omitted one** — a `file` block
without `content` does not quietly become text.

### Determinism, and why the pack is stored rather than deflated

CAP-6/CAP-7L **measured** that mORMot's static DEFLATE object emits
different bytes for `x86_64-win64` and `x86_64-linux`. That is why
`app.pwb`'s golden hash is pinned per toolchain and why `plugins.zip`
generates its registry per target.

This pack takes the other road: **every entry is stored**, so no compressor
is reached. What remains is a pure function of the entry names, their bytes,
their CRC-32s and a fixed timestamp — `TZipWrite` zeroes the whole entry
record before filling it, the version fields are compile-time constants, and
no extra field is written. Measured on the dev host: the same logical input
built through the `i386-win32` and `x86_64-win64` toolchains produced the
identical archive, byte for byte.

So `template_pack_digest` is a **four-target equality field**, not a
per-target constant. The matrix either keeps proving that or breaks loudly.

Writer discipline, reused from CAP-6 verbatim: global bytewise sort of the
canonical names, fixed DOS timestamp, no extra fields, zip64 refused, the
ratified D1 Unicode-fold collision rule, file/directory collision refusal, a
codepage round-trip check on every name, then a temp sibling that is
re-opened through `TZipRead` for a raw stored-name/method/timestamp/extra
compare **and** through the production `TZipAssetStore` for a full content
compare, and only then an atomic replace.

### What the builder refuses

- a symlink, a junction or anything that is not a regular file, anywhere in
  the tree — trusted build input is read, never followed;
- a text template carrying a CR, a NUL, a BOM, invalid or non-shortest-form
  UTF-8, or no final newline;
- an absolute host path, a home directory or a user name in **any** file,
  text or binary;
- an output path naming a credential, a key, a database or a build artifact.

## 4. The SDK dependency model

A generated project contains **application sources only**. It does not
vendor the PWeb runtime and it does not vendor mORMot.

The measured reason is what a PWeb host actually needs to compile:
`src/lib`, `src/rpc`, `src/security`, `src/webview`, `src/assets`,
`src/platform/<os>`, eight mORMot unit directories, a statics directory, and
on Win64 the CAP-3U mORMot source patch applied and restored around the
compile. Copying that into every new project would duplicate a patched
third-party tree per application and turn one security fix into an
N-project migration.

Future `pweb dev`, `pweb run` and `pweb build` supply every one of those
paths **from the SDK root associated with the executing CLI**. CAP-10D owns
packaging and finalizing the distribution; CAP-10B0 freezes only the
resolver contract that makes a generated project portable:

> **No generated file contains an absolute host path, a home directory, a
> user name or a working directory.**

Swept over every planned byte — text and binary alike — before anything is
written.

## 5. The future `create` command

Designed here, exposed by CAP-10B1:

```
pweb create NAME --ui react   --bundle-id <reverse.dns> [--output <dir>]
pweb create NAME --ui pas2js  --bundle-id <reverse.dns> [--output <dir>]
```

- **`--bundle-id` is required and never defaulted.** CAP-10A already wrote
  the reason: inventing an organisation from a project name is exactly the
  silent derivation the contract refuses, and a default would give every
  developer who scaffolds `notes` the same `CFBundleIdentifier` and the same
  Windows `AppId` — a collision in the one field whose entire job is to be
  unique.
- **`--output` names the PARENT**; the destination is always
  `<output>/NAME`. If it named the target, `--output /tmp/x` would produce a
  project whose directory is `x` and whose `name` is `notes` — a second,
  silent identity. The parent must already exist; `create` never creates an
  intermediate chain, because that is an unbounded mutation on a path the
  commit cannot undo.
- **The destination must not exist** — not as a file, not as a non-empty
  directory, not as an empty one, not as a symlink or junction, and not as a
  case-colliding sibling. Refusing the empty directory too is deliberate:
  the commit **is** a rename, and requiring nonexistence is the one rule
  that behaves identically on POSIX `rename(2)` and Win32 `MoveFileExW`.
- **No `--force`, no `--install`, no `--template-path`, no merge, no
  overwrite.**
- **Creation is offline and inert.** It writes source and configuration
  files. It does not run npm, pnpm, yarn, pas2js or FPC, download anything,
  initialise a repository or open a browser. There is no code path through
  which it could: the engine's sources name no process API, no transport and
  no package manager, and its compiled unit set links no networking unit.
- **CAP-10B0 adds no exit code.** The engine returns typed refusal codes and
  CAP-10B1 ratifies the mapping, so the frozen CAP-10A taxonomy
  (`6 > 5 > 4 > 3 > 2 > 0`) is untouched.

## 6. Identity

**`NAME` matches `^[a-z][a-z0-9]*$`, 1..64 bytes** (`PWEB_SCAFFOLD_NAME_MAX_BYTES`
= 64) — a **strict subset** of the schema-1 `name` grammar, which also
permits hyphens. `pweb create my-app` is refused, and the refusal is the
point: `PWebCliValidProgramIdent` has no hyphen, so a hyphenated NAME would
force deleting the hyphen (a lossy transformation of an identifier), adding
an option whose meaning applies only sometimes, or fixing every generated
executable to one constant name. Refusing transforms nothing.

Everything else follows with **no derivation at all**:

| schema-1 field | value |
|---|---|
| `schema` | `1` |
| `name` | `NAME` |
| `version` | `0.1.0` (`PWEB_SCAFFOLD_INITIAL_VERSION`) |
| `bundleId` | the `--bundle-id` value, verbatim |
| `ui` | the selected template's declared kind |
| `native.program` | `<native-dir>/NAME.<native-ext>` |
| `frontend.root` | the template's declared root |
| `output` | the template's declared output directory |
| destination directory | `NAME` |
| Pascal program identifier | `NAME` |
| executable base name | `NAME` |

No locale-sensitive transformation, no Unicode normalization, no lossy
punctuation removal, no case-insensitive guessing, no randomness, and no
silent replacement of an invalid character.

The generated `pweb.json` is **not a template file**: its bytes come from a
serializer with fixed key order, two-space indent, LF and exactly one
trailing newline — the shape `docs/cli-contract.md` §2 prints. It is then
re-read from the staged tree by the **frozen CAP-10A reader** and every
field compared against the planned identity, including the program
identifier the reader derives for itself. That is the step that catches a
generator and a reader which are each internally consistent and still
disagree.

## 7. Placeholders

Six tokens, one non-recursive pass:

```
{{PROJECT_NAME}}   {{PASCAL_PROGRAM}}   {{EXECUTABLE_NAME}}
{{BUNDLE_ID}}      {{PROJECT_VERSION}}  {{UI_KIND}}
```

No expressions, no conditions, no loops, no includes, no environment
interpolation, no shell expansion, no user-defined names. **A doubled
opening brace anywhere in a text template opens a token.** There is no
escape sequence and no literal form, so an unknown token and an unresolved
token are both hard failures rather than something that quietly survives
into a generated file.

That costs a real authoring constraint — a template cannot contain a doubled
brace for its own purposes, which JSX inline-style syntax does — and it is
deliberate. The alternative is a rule that passes unrecognised braces
through, and then a typo in a token name becomes a silent, permanent string
in somebody's new project.

The output of a substitution is **final**: it is appended, never rescanned,
so a value that looks like a token cannot re-expand.

In v1 `PROJECT_NAME`, `PASCAL_PROGRAM` and `EXECUTABLE_NAME` are **equal by
construction**, because `NAME` is all three. They remain three separate
contract slots so a later schema can decouple them, and the corpus records
all six projected values so that if one ever does diverge it shows up in the
evidence rather than in an executable name.

### Rendered paths

A rendered output path is checked twice, for two different things:

- it must satisfy the canonical logical-path grammar with **no placeholder
  left**, which is the syntax question;
- it must have **exactly as many `/`-separated segments as the template path
  it came from**, which is the structural question.

The second is what makes separator injection impossible rather than merely
unlikely. No identity value can contain a `/` today — but a rule that holds
because of a grammar three units away stops holding the day that grammar
widens, and nobody re-reads this file when it does.

## 8. Content kinds, line endings and file modes

Every file is classified by the **registry**, never by its extension and
never by its bytes.

| kind | rule |
|---|---|
| `text` | strict shortest-form UTF-8, placeholders expanded, no BOM, no embedded NUL, **no CR anywhere**, exactly **one** terminating LF |
| `binary` | copied byte-identically, **never** substituted, never scanned for tokens |

Both the packed source **and** the rendered result are checked, because a
substitution that introduced a CR or an invalid sequence would otherwise
reach a generated file unchallenged.

The CR rule is the one that earns its keep. Git for Windows defaults to
`core.autocrlf=true`; CAP-7F **measured** a real CRLF divergence in the
frontend corpus once already (`index.html` 188 bytes CRLF vs 177 LF). Here a
CRLF checkout does not merely diverge, it **fails the build**, and
`.gitattributes` pins `tools/templates/**` so it cannot happen in the first
place.

**File modes come from the registry**, with a two-value allowlist —
`normal` and `executable`. That is not a preference: the deterministic
writer zeroes the ZIP external attributes, so the archive cannot carry a
mode even if someone wanted it to. On POSIX the mode is applied with an
explicit `chmod` **after** the write, so the invoking shell's umask cannot
make a generated tree's permissions host-dependent. On Windows the question
is not asked at all and the evidence records `modes_applicable: false`
rather than inventing an answer.

Every generated project carries a `.gitattributes` that defaults to binary
and opts text kinds back in with `eol=lf`, so its own bytes do not depend on
whoever clones it.

## 9. The creation plan

Before anything touches a disk, an **immutable in-memory plan** is produced
carrying, for every file: the rendered output path, the exact bytes, their
SHA-256, the content kind, the intended mode and the archive entry it came
from (empty for the generated descriptor).

The whole plan is then validated at once — duplicate paths, Unicode-fold
collisions, file/directory collisions, the file count, each file's size, the
total size, each path's length, secret-classified names, and host paths in
any byte. **Nothing is discovered later, while writing.**

A test can inspect a complete plan without a single directory existing,
which is what makes the refusal matrix exhaustive rather than incidental.

### Bounds

| constant | value |
|---|---|
| `PWEB_TPL_PACK_MAX_BYTES` | 8 MiB |
| `PWEB_TPL_FILE_MAX_BYTES` | 1 MiB |
| `PWEB_TPL_TOTAL_MAX_BYTES` | 16 MiB |
| `PWEB_TPL_MAX_ENTRIES` | 512 |
| `PWEB_TPL_MAX_TEMPLATES` | 8 |
| `PWEB_TPL_MAX_OUTPUT_FILES` | 256 |
| `PWEB_TPL_PATH_MAX_BYTES` | 240 |
| `PWEB_TPL_SEGMENT_MAX_BYTES` | 128 |
| `PWEB_TPL_TOKEN_MAX_BYTES` | 128 |
| `PWEB_TPL_LIST_MAX_BYTES` | 64 KiB |
| `PWEB_TPL_ID_MAX_BYTES` | 32 |

These are private CLI implementation limits: not protocol fields, not
descriptor fields, and not raisable from the archive. The rendered-path
bound sits well under a legacy 260-character `MAX_PATH` so a generated
project stays openable by tools this CLI does not control. Every one of them
is cross-checked against this document by
`test/cap10b0/check_cap10b0_contracts.ps1` on every CI leg — a number in a
contract that nobody cross-checks is a number somebody typed.

## 10. The transaction

```
the parent must exist, be canonical, carry no reparse point, and be
writable                       (a permission question, never a probe file)
  -> the destination must NOT exist, by exact spelling AND by the
     case-folding volume's own answer
  -> a sibling staging directory, created EXCLUSIVELY
  -> every file written into it, directories one level at a time
  -> the staged tree re-read from disk and compared to the plan, byte for
     byte, path for path, mode for mode - with NO extra file
  -> the generated pweb.json re-parsed by the FROZEN CAP-10A reader
  -> rename(staging -> destination), which is the commit
```

On **any** failure the final destination remains absent, the staged tree is
reclaimed, and nothing that already existed was touched.

Exclusivity is the **kernel's**, never a check this code performs and then
hopes still holds: `CreateDirectoryW` / `mkdir(2)` fail when the name is
taken by anything, a dangling link included, and files are created with
`CREATE_NEW` / `O_CREAT|O_EXCL|O_NOFOLLOW`, which can never open, truncate,
append to or follow something that was already there.

The staging directory is `.pweb-create-<NAME>.tmp` beside the destination.
The name is **deterministic** — a random suffix would buy nothing that
exclusive creation has not already bought — and when it is already taken
(a killed earlier run, or a concurrent one) creation **refuses and names
it**. It is never removed. Reclaiming a directory this process did not
create is exactly the behaviour that turns a scaffolding tool into a
deletion tool, and the failure that would fix is smaller than the failure it
would cause.

Re-reading a tree the process just wrote is not redundant. It is the only
thing that can catch a filesystem that normalised a name, a volume that
folded a case, a mode that did not take, a short write, or a file some other
process dropped into the staging directory while it was open. The
comparison runs in **both directions**: every planned file must be there
with the exact bytes, and nothing else may be.

### The one recorded residual

Windows commits with `MoveFileExW` **without** `MOVEFILE_REPLACE_EXISTING`,
which is exclusive in the kernel and has no window at all. POSIX `rename(2)`
has no portable no-replace form — `renameat2(RENAME_NOREPLACE)` is
Linux-only, `renamex_np(RENAME_EXCL)` is Darwin-only, and neither can be
linked without pinning a libc floor this project has not agreed — so the
destination is `lstat`ed immediately before the call.

The residual is bounded and stated rather than smoothed over: an **empty**
directory created inside that window would be replaced. Nothing holding data
can be, because `rename` onto a non-empty directory is `ENOTEMPTY` and onto
a file is `ENOTDIR`. The property that matters — *creation never destroys
existing user content* — holds unconditionally on both families.

## 11. What a generated project may contain

**May:** `.gitignore`, `.gitattributes`, `.editorconfig`, source, package
metadata and exact lockfiles, a strict `pweb.json`, README and
documentation, non-secret examples.

**May not:** `.env` or `.env.*`, credentials, API keys, signing
certificates, private keys, database files, absolute developer paths, the
current user name or home directory, the working directory, tokens,
prebuilt `app.pwb` or `plugins.zip`, native binaries, `node_modules`, or
compiler output.

Dot-files are decided by an **allowlist** — exactly `.gitignore`,
`.gitattributes` and `.editorconfig` — rather than a deny-list, because the
interesting mistakes in this class are precisely the ones nobody thought to
forbid. The sweep runs over the trusted source at build time **and** over
every rendered path and byte at plan time.
